# 編碼方法 Coding Method

三層編碼 = **開放編碼（碎）→ 主軸編碼（聚）→ 選擇性編碼（挑）**。本檔說明每層怎麼做、Track A/B 差在哪、碼本欄位長什麼樣、什麼叫飽和。

核心原則一句話：**編碼是為了服務分析目標，不是為了把逐字稿分類完。** 分類完整但回答不了問題的碼本是廢的。

---

## 一、開放編碼 Open Coding（碎）

逐段讀、逐段貼碼。目標是**把資料打碎成可比較的單位**。

### 怎麼做

1. **以「一個完整的意思」為單位**貼碼，通常是 1–5 句話。不要以行為單位，也不要整段只貼一個碼。
2. **一段可以貼多個碼。** 「我都先匯出 Excel 再貼回來，很煩」同時是 `current_workaround` 和 `emotion`。
3. **碼名用受訪者的語言（in-vivo）優先。** 他說「土炮」就叫 `土炮解法`，不要翻譯成 `suboptimal_workflow`。
4. **每個碼必須綁定 `回合編號（P01-T010）+ 逐字原話`。** 沒有原話的碼等於沒有碼。編碼只讀清理稿（見 `transcript-cleaning.md`）。
5. **寧可碎不可粗。** 這階段 30 個碼很正常，第二層會合併。一開始就想貼「對的碼」會漏資料。

### 常見錯誤

| ❌ 錯 | 為什麼錯 | ✅ 對 |
|---|---|---|
| 貼 `需要批次匯入` | 這是解法/結論，不是他說的內容 | 貼 `current_workaround` + 原話「我都一筆一筆貼」 |
| 整份逐字稿只貼 8 個碼 | 太粗，之後分不出主題 | 先碎，第 5 步再合併 |
| 只貼有趣的段落 | 挑食＝結論偏誤的起點 | 全篇走過，無聊的段落也要貼或明確跳過 |
| 把訪談者的問題當受訪者的話編碼 | 那是你的話 | 只編碼受訪者發言 |
| 幫受訪者把話講順了才貼 | 改寫＝捏造 | 逐字照抄，含贅字 |

## 二、主軸編碼 Axial Coding（聚）

把碎碼聚成**主題（theme）**，並找出碼與碼之間的關係。

### 怎麼做

1. **合併同義碼。** 三個人用不同講法講同一件事 → 合成一個碼，把三句原話都掛在底下。
2. **找關係**，尤其這三種：
   - **因果**：A 發生所以 B（「沒權限」→「找 IT」→「等兩天」）
   - **條件**：只有在 X 情況下 B 才成立（「只有月底量大時才會卡」）
   - **對立**：A 與 B 互斥（「要自動」vs「不敢自動」）
3. **主題要是一句有主張的話，不是名詞。**
   - ✅「使用者不信任自動儲存，因為看不到它存了什麼」
   - ❌「自動儲存」← 這是標籤
   - ✅「權限申請的等待時間，比功能本身的缺陷更常中斷工作」
   - ❌「權限問題」← 這是分類
4. **主題數量控制在 3–7 個。** 超過 7 個通常是沒真的聚合，只是把碼換行印一次。

### 主題的檢查句

寫完一個主題，問自己：**「如果我把這句話唸給 PM 聽，他會不會問『真的嗎？誰說的？』」** 會，就是好主題（有主張、可被檢驗）。他只會「喔」，那就是標籤，不是主題。

## 三、選擇性編碼 Selective Coding（挑）

從主題裡挑出**能回答分析目標**的那幾個，串成主線。

- 對照第 2 步寫下的分析目標，逐一問：**這個主題有幫我回答問題嗎？**
- 回答不了但資料紮實的主題 → 移到「其他發現 Other findings」，保留但不進主線。
- 回答不了而且資料也薄的 → 刪，或降為一句話註記。
- **主線通常只有 1–3 個主題。** 貪心會讓報告失焦。

⚠️ 選擇性編碼是唯一允許「因為不重要所以拿掉」的階段，但**只能拿掉主題，不能拿掉反例或異例**。反例與 `outlier_view` 一律保留（見品質規則第四節）。

## 四、Track A vs Track B

| | Track A（有既定框架） | Track B（探索式，預設） |
|---|---|---|
| 什麼時候用 | 使用者給了研究問題／假設／既有碼本／既定框架 | 沒有框架，或只說「幫我看看這些訪談」 |
| 起手式 | 先用框架碼跑一遍，**再**開放編碼補 emergent | 直接開放編碼 |
| 風險 | 框架會讓你看不見框架外的東西 | 碼太碎、聚不起來 |
| 防呆 | **框架沒接住的資料必須另立新碼**，不可硬塞進既有碼。文件裡要列出「框架外新增的碼」 | 第 4 步用 code-catalog 掃漏，確認沒漏掉整個維度 |

**Track A 的必要動作**：在文件裡單獨列一節 **「框架外的發現」**，寫出既有框架沒有預期到的碼。沒有這一節的 Track A 分析，等於只是拿資料去驗證你本來就相信的事。

## 五、碼本欄位 Codebook Fields

主題編碼表（產出①）每一列的欄位：

| 欄位 | 說明 | 必填 |
|---|---|---|
| `code_id` | C01、C02… | ✅ |
| 碼名 | 中文為主，可附英文 key | ✅ |
| 定義 | 一句話說明這個碼涵蓋什麼 | ✅ |
| 納入 | 什麼樣的內容算這個碼 | ✅ |
| 排除 | 什麼樣的內容**不算**（最容易省略，但最有用） | ✅ |
| 人數 | 幾個人提過（P 的數量） | ✅ |
| 次數 | 總共被提到幾次 | ✅ |
| 代表引句 | 1–2 句逐字原話 + 回合編號（`P01-T010`） | ✅ |
| 主題 | 屬於哪個主題（T1/T2…） | ✅ |
| `failure_mode` | 僅 `pain_point` 類需要 | 痛點必填 |

**「排除」欄位為什麼必填**：它是碼本唯一能防止碼膨脹的機制。沒有排除規則，`pain_point` 最後會吃掉半份逐字稿。
例：`trust_risk` 的排除 =「單純抱怨慢、但沒提到出錯代價的，歸 `pain_point` 不歸這裡」。

## 六、飽和度 Saturation

**判準**：把逐字稿依分析順序排好，看**最後 20% 的資料還有沒有長出新碼**。

| 情況 | 判定 | 文件裡怎麼寫 |
|---|---|---|
| 最後 1–2 份沒有新碼，只是重複既有碼 | 已飽和 | 「已達飽和（最後 2 份未產生新碼）」 |
| 最後 1 份仍長出 ≥2 個新碼 | **未飽和** | 「**未飽和**，最後一份仍產生 N 個新碼，樣本可能不足，結論為暫時性」 |
| 樣本 ≤3 份 | 不適用 | 「樣本量小（n=X），不評估飽和度，結論為暫時性」 |

**未飽和不是失敗，是重要的發現** —— 它告訴團隊「還要再訪幾個人」。一定要寫出來，不可因為結論看起來不夠漂亮就略過。

同時建議寫一句「還缺誰」：哪種角色/情境完全沒有被訪到（例如全是老手、沒有新手；全是同一部門）。這是最常見、最便宜的後續行動建議。
